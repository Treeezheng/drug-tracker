# Server security review — 2026-09-13

Scope: current working tree based on `3aa3868`, including uncommitted changes, reviewed independently from prior security documentation. Review covers local/cloud HTTP handlers, SQLite/PostgreSQL repositories, envelope validation, client cryptographic primitives, authentication, request limits, deletion and logging. No production endpoint, personal database, real password or encryption key was accessed. This is a focused engineering review, not a penetration-test certification or legal opinion.

## Reproduced findings before remediation

### P1 — Anonymous requests can exhaust the whole cloud login budget

At review start, `server/cloud.mjs:106–120` keeps a single login counter (30 requests/15 minutes) and registration counter (10/hour), and routes at lines 206/221 charge them before parsing JSON. PostgreSQL stores the same global counters keyed only by operation (`server/cloud-postgres.mjs:147–154`). An isolated server with the default settings returned **400 for 30 unauthenticated one-byte malformed login bodies, then 429 for correct credentials**. No account knowledge or password guessing was needed to deny every user's login. Forging the allowed Origin outside a browser is sufficient; Origin checks are CSRF controls, not bot authentication.

Fix requested: validate small bodies before charging an account budget; isolate login quotas by normalized username digest; isolate registration by a verified transport source; retain bounded password-hash concurrency instead of a small global timed lockout. Quotas shared through PostgreSQL must remain isolated across dynos.

### P2 — Local writes can complete after their session was revoked

`server/index.mjs:668` authenticates before asynchronous body reads; profile/entity writes at lines 717–722 and import at 670–689 do not recheck that session afterward. Reproduction: send the first byte of an authenticated profile PUT, complete logout (200), finish the PUT body: **the PUT still returns 200 and writes**. Cloud storage already revalidates sessions inside its transaction and is not affected by this reproduction. Local account deletion also has an asynchronous password check and needs session revalidation in addition to its existing fresh password-hash check.

Fix requested: recheck the same owner's live session immediately before each synchronous local mutation, including import and account deletion. A concurrent logout/password reset must make the delayed mutation fail with 401.

### P2 — Cloud account/vault removal is absent

Authenticated `DELETE /drug/api/account` returned **404**. `server/cloud.mjs:249` rejects this route; neither cloud repository provides account deletion. SQLite's encrypted-vault table does not have an account foreign key (`server/vault-store.mjs:79–86`), so deleting an account row alone would leave ciphertext behind. PostgreSQL has cascading foreign keys but no exposed deletion transaction. This is a missing privacy control, not evidence of an unauthorized disclosure.

Fix requested: same-origin authenticated, owner-bound deletion with fresh account-password confirmation; atomically remove that owner's account, vault and all sessions, with concurrent saves/login/logout covered. Wrong credentials must preserve data. Do not describe logical deletion as immediate erasure of provider backups.

### P2 — Large encrypted requests have no aggregate concurrency budget

`server/cloud.mjs:15,173–193` bounds each encrypted request to approximately 21.3 MB but buffers it and then decodes/parses it. Several parallel uploads can hold multiples of this amount plus JSON/envelope copies. GET responses can likewise hold a large serialized vault while a client reads slowly. There is no per-process or per-owner gate. This is a code-supported resource-exhaustion risk; no memory exhaustion or destructive load test was performed.

Fix requested: cap concurrent large vault operations and release reservations on completion, connection close, parse/validation failure and storage failure; return a brief 429 Retry-After so clients can retry without losing their draft.

## Controls independently checked

- Cloud passwords use salted scrypt (`N=32768,r=8,p=1`) and constant-time comparison; unknown accounts use a dummy hash. Session tokens are random 32-byte values stored only as SHA-256 hashes. Cloud cookies are Secure/HttpOnly/SameSite=Strict and scoped to `/drug/` for HTTPS.
- Host and Origin are compared exactly; unsafe methods require Origin; cross-site fetches are rejected. `X-Dose-Owner` must match the session. The cloud API exposes encrypted-envelope storage, not local plaintext record endpoints. Relevant implementation: `server/cloud.mjs:26–44,127–168,241–249` at review start.
- Envelope parsers strictly check protocol/version, owner, exact fields, canonical base64url, IV/ciphertext sizes and KDF bounds (`server/vault-store.mjs:21–67`). The server intentionally cannot authenticate ciphertext; the browser authenticates AES-GCM with owner/type/version context before applying restored data (`src/lib/vault-crypto.ts:70–93,199–250`). Modified ciphertext is stored only as opaque bytes and fails client decryption.
- Cloud responses use no-store, no-referrer, nosniff, frame blocking, same-origin CSP and disabled camera/microphone/geolocation. Only an edition-checked cloud HTML snapshot is served. Static path checks reject traversal and symlink escape. Current handler errors do not log bodies, ciphertext, passwords, URL credentials or stack traces (`server/cloud.mjs:275–283`). PostgreSQL idle-connection errors also avoid detailed logging. Local unexpected errors log only a generic message plus error code/name (`server/index.mjs:745`).
- PostgreSQL uses parameterized statements, bounded connections/timeouts, certificate verification with `rejectUnauthorized:true`, explicit trust roots when configured, and removal of URL options that could override TLS. Plaintext database transport is permitted only through an explicit numeric-loopback test option, rejected by the Heroku entry point.
- Existing PostgreSQL tests directly observe row-lock blocking and test cross-instance sessions, compare-and-swap and whole data/key-pair atomicity. Local/cloud database locations remain separate; cloud initialization rejects a local-edition schema.

## Operational and cryptographic boundaries

This source review does not verify the deployed Heroku release, external TLS termination, actual PostgreSQL certificate chain, DNS, production environment variables, staff access controls, backup retention/restore handling, log drains, incident response or dependency supply chain. Tests use synthetic loopback traffic; they do not prove protection against a distributed flood.

Application logging is different from hosting-provider logging. Heroku documents router logs containing request path/query, IP and timing, plus platform Network Error Logging. A policy must not promise that the provider receives no metadata merely because application code omits analytics. Query-string redaction is a platform setting; this review has not verified it. See [Heroku HTTP Routing](https://devcenter.heroku.com/articles/http-routing#heroku-router-log-format).

For source quotas, Heroku documents that its router appends its observed client IP to the **right** of X-Forwarded-For, while warning that forwarded headers in general are untrusted. Only the explicitly selected Heroku deployment adapter may use that final validated IP, only for abuse quotas. Non-Heroku deployments must use the transport peer unless separately configured and audited. Arbitrary leftmost values cannot be treated as trusted. See [Heroku headers](https://devcenter.heroku.com/articles/http-routing#heroku-headers).

Account metadata, session hashes, ciphertext size/timestamps and operational metadata remain visible to the server/provider. A weak vault passphrase permits offline guessing against a stolen wrapped key. The operator serves the client JavaScript and could change future delivered code; open-source availability does not prove that a browser received an audited build. AES-GCM authenticates a ciphertext's contents, but these envelopes do not provide independent historical freshness against a malicious server replaying an old valid snapshot. Local records, exports, browser drafts, process memory and provider backups each have distinct retention properties. None should be described as automatically or forensically erased by a database DELETE.

### Session lifetime and account security

- `server/cloud-session.mjs:1–8` limits cloud sessions to **24 hours absolute**, without activity-based extension. Both repositories cap legacy expiration values from the original session creation time during startup. Restart does not renew an old cookie; an account older than the new limit must sign in again. Invalid creation metadata produces an unusable session rather than a longer lifetime. No account or vault data is deleted by this change.
- `server/cloud.mjs:226–229` exposes authenticated, mandatory-owner-header `GET /security`. The response contains only current-session creation/expiry timestamps, active-session count and the 24-hour lifetime. It does not add IP, user-agent, device fingerprint or health-activity logging.
- `server/cloud.mjs:291–319` provides `POST /auth/verify-password`, `POST /auth/logout-all` and `POST /auth/change-password`. All require the authenticated owner header and fresh account-password confirmation, share the account attempt budget and bounded hashing work, then revalidate the current session and expected password hash inside a repository transaction. A wrong current password is 403; a revoked session, changed account or stale password snapshot is 401. Extra fields and weak replacement passwords are rejected.
- Verification returns `{ok:true}` without a new cookie or lifetime extension. All-device logout deletes all sessions, including the current session, but leaves encrypted data unchanged. Account-password change atomically changes the salted scrypt hash, removes every prior session and creates one replacement 24-hour session; it does not rewrap a vault key or modify ciphertext. PostgreSQL uses the existing account→session lock order to serialize these operations with saved data and login. A queued login or verification using an obsolete hash/session fails after the change.
- Bootstrap, public registration and account-password change use the same locally evaluated `accountPasswordError` policy as the browser (`src/lib/password-policy.mjs`; imported at `server/cloud.mjs:12,36–40`). New passwords need at least 15 Unicode code points, fit the 256 UTF-16-unit maximum, be well-formed Unicode and reach zxcvbn score 3 using local dictionaries plus the username. No password-checking network service is contacted. Existing weak passwords remain accepted for login and current-password confirmation so the owner can upgrade them. Scrypt parameters remain `N=32768,r=8,p=1` with independent random salts. Only inexpensive syntax and length validation runs before quotas. Registration strength scoring runs after the source quota, inside the same two-slot resource gate as hashing; replacement-password scoring runs after the account quota and successful current-password verification inside that gate. Well-formed weak passwords consume their own subject quota, preventing repeated unmetered scoring.

### Encrypted-envelope compatibility

`server/vault-store.mjs:43–64` retains data envelope version 1 and permits either legacy wrapped-key version 1 (PBKDF2-SHA256, 600,000–2,000,000 iterations) or wrapped-key version 2. Version 2 has one exact KDF object: `{name:'Argon2id',version:19,memoryKiB:65536,iterations:3,parallelism:1,salt}` with a canonical 16-byte salt. Different algorithms, extra fields, work factors, memory sizes or parallelism are rejected before storage. The server performs no KDF or decryption for these envelopes.

The existing revision-checked PUT still stores the data/key pair atomically. A data-v1/key-v2 pair is valid; no key-only endpoint or partial overwrite was added. This supports client rewrapping and complete data-key rotation without giving the server an encryption password or recovery key. Only the cloud app CSP adds `'wasm-unsafe-eval'` for the locally bundled Argon2 WebAssembly implementation; JavaScript `'unsafe-eval'` remains absent, and public legal pages remain script-free.

Rotation cannot erase a copied older ciphertext or previously exposed plaintext. Legacy envelope support is intentional, so the server's shape validation alone is not a promise that every existing vault has already upgraded to Argon2. Verification of new-client defaults, key-rotation acknowledgments and browser resource use belongs to the accompanying client checks.

## Follow-up: single-password OPAQUE replacement

The user subsequently chose a single-password design and explicitly retired the old migration/user flow. This section supersedes the earlier public raw-password API descriptions. Those earlier results remain historical evidence, not current deployment claims. New working-tree accounts use pinned `@serenity-kit/opaque` 1.1.0, with browser-only Argon2id key stretching and export-key-derived v3 wrapping. Raw password routes and legacy sessions are disabled in production; the explicit compatibility test option retains synthetic regressions without removing existing stored data. CLI bootstrap is also disabled before opening a database.

### Current controls inspected

- `server/cloud.mjs:245` dispatches bounded OPAQUE requests through existing exact-origin/host guards, source extraction, work reservations and owner/session checks. `server/cloud-opaque.mjs:10` enforces exact JSON fields and canonical fixed-length protocol messages; the primary protocol accepts no master password, export key, full recovery code or DEK. `server/vault-store.mjs:43` accepts exactly data-v1 and wrapped-key-v3 metadata, with the fixed OPAQUE-export/SHA-256 context. These shape checks do not establish ciphertext authenticity; browser decryption does.
- `server/cloud-opaque.mjs:30` initializes a durable setup and exposes only its public key. SQLite setup/migration is in `server/cloud-sqlite.mjs:66` and its repository methods; PostgreSQL setup and schema version 3 are in `server/cloud-opaque-postgres.mjs:18,57`. A missing setup with existing OPAQUE accounts fails closed. Concurrent startup has one durable winner. Setup is stored with the password files: database theft can permit offline guessing, so this is not an independent secret-store claim.
- `server/cloud-opaque.mjs:40` creates 120-second, digest-addressed challenges. The stores atomically admit and consume them with source, kind, username, owner, auth-version and applicable session binding. Pending caps are 1000/40/12 for global/source/username; separate cumulative source and account quotas prevent consumed handshakes from resetting the budget. Existing-account and fake-record login starts have the same response fields; this does not claim indistinguishable timing across every quota/database state.
- `server/cloud-opaque.mjs:87` verifies PAKE before session creation. PostgreSQL `opaqueOwner` and transactional commits recheck current auth version and session under account-first locks. Password change preserves exact data ciphertext and the existing recovery verifier. Recovery/rotation update credentials, complete ciphertext/key pair and replacement session together, with CAS. All-device logout increments auth version, so even a login challenge already claimed before revocation cannot recreate a session afterward. Ordinary PUT cannot change an OPAQUE key wrapper.
- `server/cloud-opaque.mjs:120` grants recovery access only after constant-time comparison of a hash of the independent 32-byte authentication half. It never receives the full code or its DEK half. Final recovery rechecks original recovery hash/auth version and vault CAS before replacing everything atomically; failures leave the existing record usable. An authorized grant can read ciphertext, so leaked recovery-auth material is still security-sensitive even without the DEK half.

### Concrete issues found and corrected before freeze

1. **P2, inconsistent unknown recovery:** the initial fake recovery username used a colon, rejected by the SQLite challenge validator but accepted by PostgreSQL. Unknown-owner `/recover/start` returned 400 instead of the real-owner 200 shape. It now uses a bounded valid hash-derived placeholder. The real SQLite HTTP regression verifies both start responses have exactly the same fields, no username/vault disclosure, and wrong authorization returns 401.
2. **P2, overly small pending budget:** three legitimate abandoned login/recovery attempts exhausted the original per-username pending limit of three. The cap is now 12 per username/40 per source with the same short TTL and global cap. A cumulative source quota was added so increasing pending capacity does not permit unlimited consumed challenge attempts across known names.
3. **P2, recovery retry availability (client cross-review):** choosing the same master during recovery and losing the request before commit plus the reconciliation response left no original snapshot for distinguishing old state from a committed rotation. The client owner now retains the authorized old snapshot. Its real HTTP regression verifies same-password retry preserves records, increments exactly once and revokes old sessions. No service protocol change was needed.
4. **Test-only disconnect ordering:** full-load execution exposed that a client `ECONNRESET` did not prove the server had received the disconnect before the blocked owner query was released. The PostgreSQL regression now waits for the server-side socket-close event before releasing the database barrier. Original null-vault and next-save-success assertions remain; production handling was not loosened.
