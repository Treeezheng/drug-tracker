# Single-password cloud protocol

This document describes the single-password OPAQUE contract implemented in this source tree. The [two-password prototype](editions-and-encryption.md) and [candidate review dated 13 September 2026](opaque-release-review-2026-09-13.md) are historical records. Deployment evidence must identify the source commit, verified build and sampled live assets; see [verification and limitations](security-reviews.md#verification-and-limitations). A protocol document alone does not establish which bytes a website currently serves.

The dependency is pinned to `@serenity-kit/opaque` 1.1.0. Its registration and login messages are sent over the existing exact-origin HTTPS API. New master passwords and OPAQUE export keys never reach the server. The shared OPAQUE session key is **not** used to wrap the data key. [Official integration](https://opaque-auth.com/docs/get-started/add-to-existing-project), [library source](https://github.com/serenity-kit/opaque).

OPAQUE `userIdentifier` is the account's stable UUID. Both sides use identifiers `{client: normalizedUsername, server: 'drug-tracker:opaque:v1'}`. The client applies fixed Argon2id 65,536 KiB / 3 iterations / parallelism 1 at finish. Password-strength checks are client-side in this protocol: a server that never receives the password cannot independently run zxcvbn on it.

The server setup is initialized once in a dedicated shared database row and reused across processes/restarts. An optional operator override must match the existing value. It is not a data decryption key, is never returned by an API/export/log, and is not regenerated for an existing OPAQUE database. Theft of the database **including** setup and password files permits offline password guessing; this design does not claim those secrets occupy independent security boundaries.

All paths below are relative to `/drug/api/auth/opaque`. JSON objects have exact fields except optional registration `name`. Successful account responses contain `user:{id,name,username,authMode:'opaque-v1'}`, a current `vault` snapshot where specified, and the ordinary Secure/HttpOnly/SameSite cookie. Primary login never selects a raw-password fallback from an untrusted mode response. Production exposes only the new OPAQUE account flow. Old raw-password and migration routes are disabled; an explicit non-environment test option enables synthetic legacy compatibility fixtures. Existing stored records are not automatically deleted.

| Request | Body | Result |
|---|---|---|
| GET `/config` | none | protocol, public server key, server identifier |
| POST `/register/start` | username, name?, registrationRequest | challengeId, ownerId, username, registrationResponse, expiresAt |
| POST `/register/finish` | challengeId, registrationRecord, dataEnvelope, keyEnvelope, recoveryAuthHash | user, vault, cookie; atomically creates account + vault + recovery verifier + session |
| POST `/login/start` | username, startLoginRequest | challengeId, loginResponse, expiresAt; unknown/legacy accounts use the library's fake-record path |
| POST `/login/finish` | challengeId, finishLoginRequest | user, vault, cookie only after proof and current authentication-version verification |
| POST `/reauth/start` | action, startLoginRequest | challengeId, loginResponse, expiresAt; requires current cookie and owner header |
| POST `/reauth/finish` | challengeId, finishLoginRequest | reauthGrant, action, expiresAt; no cookie change |
| POST `/recover/start` | ownerId, registrationRequest | challengeId, expiresAt |
| POST `/recover/authorize` | challengeId, recoveryAuthSecret | recoveryGrant, ownerId, username, registrationResponse, vault, expiresAt |
| POST `/recover/finish` | recoveryGrant, registrationRecord, expectedRevision, dataEnvelope, keyEnvelope, recoveryAuthHash | user, vault, replacement cookie |
| POST `/change/start` | reauthGrant, registrationRequest, expectedRevision | challengeId, ownerId, username, registrationResponse, expiresAt |
| POST `/change/finish` | challengeId, registrationRecord, expectedRevision, dataEnvelope, keyEnvelope | user, vault, replacement cookie; unchanged data ciphertext, rewrapped existing DEK |
| POST `/rotate-recovery` | reauthGrant, expectedRevision, dataEnvelope, keyEnvelope, recoveryAuthHash | user, vault, replacement cookie; same OPAQUE record, new DEK and recovery verifier |
| POST `/migrate/start` — synthetic tests only | legacyPassword, registrationRequest, expectedRevision | challengeId, ownerId, username, registrationResponse, expiresAt; production returns 410 |
| POST `/migrate/finish` — synthetic tests only | challengeId, registrationRecord, expectedRevision, dataEnvelope, keyEnvelope, recoveryAuthHash | user, vault, replacement cookie; production returns 410 |

Actions are `delete-account`, `logout-all`, `change-password`, and `rotate-recovery`. For OPAQUE accounts, existing `DELETE /drug/api/account` and `POST /drug/api/auth/logout-all` accept only `{reauthGrant}`. Legacy raw-password routes reject OPAQUE accounts. All-device logout also increments the authentication version, invalidating a previously claimed but unfinished PAKE login.

Challenges and grants expire after 120 seconds, are single-use, and are shared across PostgreSQL/SQLite processes. Only a SHA-256 digest of each random 32-byte handle is stored. They bind purpose, normalized username, owner, authentication version, transport-source digest and, where applicable, current session digest and vault revision. Pending state is bounded globally (1,000), per source (40), and per username (12), in addition to cumulative source/account rate quotas and process work gates. Login/recovery starts have a combined source budget of 120 per 15 minutes by default, alongside the per-account budget of 30; consuming a handshake does not reset either budget. Source buckets can be shared by users behind one NAT. Consuming an expired matching handle removes it; a wrong kind/source cannot consume a different purpose's handle. Validation failures do not change live account/vault data.

Recovery code: `DTR1.<ownerId>.<auth32B-base64url>.<DEK32B-base64url>`. Both secret parts are independently random. The server stores lowercase hex SHA-256 of the **decoded auth bytes**, and only `/recover/authorize` receives that auth part. The DEK part and complete code stay in the browser. Authorization gives temporary access to the old ciphertext without consuming the old recovery verifier. Final recovery checks its original authentication version and recovery hash plus vault CAS, then atomically replaces the OPAQUE record, ciphertext/key pair, recovery hash and all sessions. A failed or abandoned operation leaves the prior recovery code and records intact. Migration likewise checks the original legacy hash/session/version and vault revision; an empty legacy vault may migrate at revision 0.

Data envelopes remain version 1. Wrapped-key version 3 has the same AES-256-GCM fields and exact KDF `{name:'OPAQUE-export',hash:'SHA-256',context:'drug-tracker:opaque:v1',salt}` (16-byte salt). The browser derives the wrapping key from its 64-byte export key via HKDF-SHA256; IV is 12 bytes, wrapped ciphertext 48 bytes. Ordinary vault PUT cannot change an OPAQUE account's key envelope; only the specialized atomic credential operations can do so. Older snapshots and already downloaded data remain outside revocation guarantees.

Historical verification recorded for the [13 September 2026 candidate](opaque-release-review-2026-09-13.md) used temporary synthetic databases, not production: SQLite/API/legacy-composition selection 41/41; real PostgreSQL/OPAQUE/configuration selection 25/25, zero skips; strict envelope storage 9/9; retired CLI bootstrap rejection 1/1. The client owner reported real HTTP composition 8/8, including retained pending recovery bundles and same-password recovery retry after a pre-commit failure. Selections overlap and must not be summed as unique coverage or presented as the current suite count. Later results are recorded in the [dated review history](security-reviews.md). No CLI bootstrap, secret environment entry or manual setup-secret regeneration is required for primary registration.
